## Design Specificity Verdict

**LLM assessment: category-interchangeable.** Swap the strings "5-hour window" and "Week" and this panel drops unchanged into a Cloudflare quota popover, a Vercel usage widget, or a disk-space utility. The dark card (`#1b1f26`, 12px radius, `rgba(255,255,255,.12)` hairline), the 5px pill track (`#3a4150`), and the traffic-light triad are each the default you get when nobody chooses. Three specific losses:

- **The camel never appears in the product.** The metaphor is doing real semantic work — a reserve carried across a distance with no resupply is exactly what a rolling quota window is — and it is spent entirely on the app icon and the README hero. The empty state, which has ~90px of dead air and nothing to say, is where it belongs.
- **Two windows of genuinely different nature are drawn identically.** The 5-hour window is a sprint that refills three or four times a working day; the 7-day is background weather. Same pill, same width, same weight, same everything. Nothing in the geometry says which one is about to bite.
- **Velocity is discarded.** The app polls every 30 s and therefore sits on the derivative, then throws every prior sample away. `limits::worst()` — the function that encoded "here is the number that matters" — is dead code called only by its own test (verified: the only two references in `src-tauri/src/` are its definition at limits.rs:52 and its assertion at limits.rs:146). Burn rate is the one feature no generic dashboard would ship, and it is the one feature absent.

**Deterministic scan.** `detect.mjs --json src/index.html` and `--json src` both return `[]`, exit 0. Assessment B validated the instrument with a canary file (Inter + gradient `background-clip:text` + overshoot cubic-bezier) that produced 3 static and 16 browser findings — so the clean result is a real pass, not a silent no-op. The static engine does not evaluate contrast or type size; those rules live only in the browser engine, which required a scratch copy because `puppeteer` is not installed (the shipped skill was left unmodified).

Browser engine, identical in all four states: **one finding, `flat-type-hierarchy` (warning)** — "Sizes: 11.5px, 12px, 13px, 15px (ratio 1.3:1)". Treated as a **false positive in kind but true in fact**: the rule assumes a page with a headline tier, and this surface's largest type is a 15px metric. The real defect underneath it is that four sizes inside 200px read as one continuous grey ramp rather than a hierarchy.

## Overall Impression

The Rust is opinionated and full of hard-won judgment — the `.max(2)` minimum bar height with its comment "a vanished bar reads as a broken icon, not an empty tank", the reset-rollover rule, the Down/Up click debounce, the panel that grows exactly 48px for exactly the row that appeared. The panel is where that authorship stops. It is a competent, restrained, well-built readout that answers "how much" and refuses to answer "will I make it" — despite polling the data that would answer it every 30 seconds.

The single biggest opportunity: one sentence at the top of the panel stating the conclusion (`On pace to run out ~18:12 — 40 min before reset` / `On pace to last the window`), backed by a small ring buffer of samples and `worst()` finally getting its caller back. That one line converts a readout into an answer, and it is the only proposal here a generic dashboard could not ship.

## What's Working

1. **Remaining-not-used, enforced at the boundary.** limits.rs:97 flips `used_percentage` exactly once, and every downstream surface — tray bar height, panel bar width, colour class, tooltip — speaks the same direction. This works because a depleting gauge maps to the user's actual question and has an intuitive terminal state: the bar reaching zero *is* the event.
2. **Sized to content, not to a template.** `PANEL_H: 200.0` / `PANEL_H_WITH_UPDATE: 248.0`. Most menu-bar apps ship one fixed height and let empty states rattle inside it. Growing exactly the height of the row that appeared is what separates "instrument" from "web page in a box" at a two-second dwell.
3. **Severity dual-encoded as colour *and* length**, on both the tray icon (height) and the panel (width). A deuteranopic user still reads "nearly empty" from geometry when green and amber collapse into one muddy tone. It is the best accessibility decision in the codebase and it was not flagged as one — which is why it is undone at the extremes (see P0-2).

## Priority Issues

### [P0] The empty state tells first-time users something that is false, and offers no way out

**What.** index.html:23–24 reads "No limit data yet. Camel reads what the Claude Code status line writes. Talk to Claude Code once and the bars appear." Talking to Claude Code does not make the bars appear: the user must first add the `jq` snippet from README.md:59–64 to their statusline script. The panel never says this and contains no link, button, or path. The same screen also appears when the JSON is malformed (limits.rs `parse` returns `None` on any parse failure), so "not set up" and "set up wrong" are one screen.

**Why it matters.** This is the entire first-run experience for every GitHub visitor who is not the author, and the loop it creates — do the thing, nothing happens, do it again — has no floor. Highest-churn defect in the product.

**Fix.** State the actual precondition and add the action that closes the loop: "Camel reads `~/.claude/statusline-last.json`. Your Claude Code status line has to write it — two lines in your statusline script." plus a `Show me how` button opening the README setup anchor. Add a second sub-state for "found the file, couldn't read it — expected `rate_limits.five_hour`".

**Suggested command:** `/impeccable onboard`

### [P0] At 0% the bar renders as nothing; stale data renders as confident fiction

**What.** Two failures at the same moment of maximum stakes, both verified in source:
- main.js sets `fill.style.width = '${win.remaining}%'` and `.bar span` declares `width: 0` with no `min-width` — at 0% the element has zero width and the row shows an entirely empty track, visually identical to a broken bar. The Rust side guards this exact case (`heights()` has `.max(2)` with the comment about a vanished bar reading as broken); the CSS has no equivalent. The lesson was learned on one surface and not carried to the other.
- When `now >= resets_at`, limits.rs correctly reports `remaining: 100` but leaves `resets_at` in the past — so the panel prints a past wall-clock time as a future reset ("resets Wed at 22:33") with a countdown frozen at "in 0 min" forever, in bright green. This is not exotic: it is every morning where no session has run since the last rollover.

**Why it matters.** The whole value proposition is trustworthiness at a glance, and both bugs fire precisely when trust matters most — at exhaustion, and after a gap. A user who once sees 100% on stale data and then hits a limit mid-task stops opening the app.

**Fix.** `.bar span { min-width: 3px }`, mirroring the Rust rule with the same intent. When `now >= resets_at`, stop rendering the stale absolute time — show "refilled — no session since". Escalate staleness past ~10 minutes into the row itself (desaturate the fill, drop the colour class to neutral) rather than leaving it to the dimmest text in the app; confident colour must be reserved for confident data.

**Suggested command:** `/impeccable harden`

### [P1] The panel never says what the number is a percentage *of*

**What.** `73%` carries no noun — not "left", not "remaining", not "used". The tray tooltip says it ("Camel — 5h 73% · week 95% left") and the README says it; the panel, the surface built to give the full picture, drops the one word that disambiguates. Compounded by "Week", which for a rolling 7-day window implies a Monday reset — the shipped screenshot shows it resetting Friday.

**Why it matters.** Every progress bar the user has ever seen fills *up* as things get *worse*. Camel inverts that, so correct reading rests entirely on colour — which fails for the ~8% of male users with colour-vision deficiency, and for anyone glancing at a yellow bar wondering whether yellow means half gone or half used.

**Fix.** One word in the header row: `5 hours · 73% left` / `7 days · 95% left`. Rename "Week" to "7 days" so the rolling nature is implicit, then align tooltip and README to that exact vocabulary — one name per window across three surfaces.

**Suggested command:** `/impeccable clarify`

### [P1] The panel answers "how much" but never "will I make it", despite holding the data

**What.** At 9% with 47 minutes to reset, the user sees two facts and must do the arithmetic Camel is better positioned to do. The app polls every 30 s and holds exactly one snapshot; every previous sample is discarded. `worst()`, the function encoding which window binds, is dead code.

**Why it matters.** "Am I about to be cut off mid-refactor?" is the actual job. Everything on screen is an input to that question; the answer is absent. Operate mode is judged on whether the user's next action changes, not on whether the data is displayed.

**Fix.** Keep a ring buffer of `(t, remaining)` in Rust — 20 samples is 10 minutes and costs nothing. Derive a burn rate and put one sentence at the top: "On pace to run out ~18:12 — 40 min before reset" (red) / "On pace to last the window" (calm grey) / "Idle — no burn in the last 10 min". Then use `worst()` for what it was written for: the window that sentence is about goes first, the other is demoted.

**Suggested command:** `/impeccable shape`

### [P2] The README hero screenshots ship impossible data

**What.** `docs/screenshots/panel.png` and `update.png` both show "5-hour window … resets Thu at 17:30 · in 23 h" — verified by reading the image. A 5-hour window cannot reset 23 hours out. Root cause is in the harness fixture: `_camel_shot.mjs` rolls its 17:30 target to tomorrow whenever 17:30 has already passed, and the shots were taken in the evening. `low.png` ("in 47 min") is the only correct one.

**Why it matters.** These are the first two images every GitHub visitor sees, in a README whose entire pitch is that the numbers are trustworthy and local. Anyone who knows what a 5-hour window is spots the contradiction immediately.

**Fix.** Clamp the fixture (`five_hour.resets_at = now + 2h`, `seven_day.resets_at = now + 4d`), assert in the harness that the 5-hour reset is never more than 5 hours out so it cannot regress, and reshoot. Note the GitHub camo cache: a corrected PNG under the same filename keeps serving the old pixels, so reshoots need new filenames.

**Suggested command:** `/impeccable polish`

## Persona Red Flags

**Alex (power user, 20+ opens/day).** `resetIn` rounds with `Math.round(mins/60)`, so 91 minutes prints "in 2 h" — a 29-minute error on a five-hour budget, erring toward over-promising time, on the number he plans work around. Everything from 60 to 2879 minutes collapses to whole hours, and hours is exactly the wrong unit for the window that matters most; it needs "1h 31m". The panel is identical on his 300th open as on his first: no trend, no burn rate, no preference for what the tray weights.

**Sam (accessibility).** The two AA failures are the critical percentage (4.22:1) and the staleness warning (4.28:1) — the two elements most needed under time pressure. Fixes: `#e5484d` → `#ff6369` (~5.4:1), `#7c828d` → `#959ba6` (~6.0:1). The empty track at 1.61:1 against the card makes the "how much is missing" half of the bar nearly invisible. `#update` has `outline: none` with no replacement and zero `:focus-visible` rules in the stylesheet — rest and keyboard-focus computed styles are byte-identical, so the only interactive element has an invisible focus state (hover feedback is mouse-only). No `role="progressbar"`/`aria-valuenow` on the bars, so the redundant length encoding that saves CVD users does not exist for a screen reader; no `aria-live` on values that mutate under `limits-changed` while the panel is open. Font sizes are hardcoded px in a WKWebView, so macOS "larger text" cannot reach this panel.

**Riley (edge cases).** "resets today at 09:00 · in 0 min" shown at 14:00 — the rollover case above. 0% renders an invisible bar. `hour12: false` is hardcoded alongside locale `'en-US'`, so a US user with a 12-hour Mac clock is shown 17:30 — locale pinned to US, clock convention pinned against US default. A 7-day window resetting exactly 7 days out prints today's weekday name, ambiguous between "in 20 minutes" and "in a week" (saved only by the countdown beside it). `PANEL_H` is a hand-maintained constant against content it cannot measure, with `overflow: hidden` — any string growth clips silently, with no scroll and no indication. The update installs on a single click with an empty progress closure, then restarts: on a slow connection the panel just sits there, then the app vanishes and returns, so Riley clicks twice.

**Casey (mobile): n/a.** A tray-only desktop binary with a fixed 320px non-activating NSPanel positioned against a physical menu-bar rect. No responsive dimension, no touch target, no viewport. The adjacent concern — that 320px cannot adapt — is Riley's clipping issue, not Casey's.

## Minor Observations

- Proximity is inverted: `.top { margin-bottom: 6px }` against `.reset { margin-top: 5px }` puts the bar 1px closer to the line below than to the label it belongs to, so it optically groups downward.
- "Update to v0.1.3 — install" is a sentence with a command bolted on by em-dash; macOS convention is verb-first ("Install v0.1.3"), and the footer already shows the current version, making "update to" redundant.
- The update button shares the green family with the OK bars, so in the update state there are three green things and no designated stop for the eye. The single action should not share a hue with ambient status.
- No popover beak. The panel is centred under the tray icon with a 6px gap but nothing ties it to the icon, so it reads as "a window near the menu bar" rather than "the menu bar's window". Defensible, but it is why the association feels loose.
- The reset row spends a full line on two encodings of one fact, twice, in a panel with a 2–5 second dwell.
- `age()` is computed from file mtime, so a `touch` with no content change reads as fresh: "updated just now" is a statement about the filesystem, not about the data.
- `#age` is the one changing-digit element without `tabular-nums`, so it shifts as the number of minutes changes width.
- The panel has no identity beyond "Camel v0.1.2" in the dimmest text in the footer.

## Questions to Consider

1. Why two bars at all? The user has one question — when do I stop being able to work? — and that is always `min(5h, 7d)`, the function you already wrote and then orphaned. What would this look like with one number, large, and the other window as a one-line footnote?
2. What is the panel *for*, given the tray icon already answers "how much" and the tooltip gives exact percentages on hover? If the answer is "burn rate and projection", why isn't that the panel's content?
3. Why does Camel only ever speak at bad moments? There is no state where opening it is good news. What would "your 5-hour window just refilled — you're clear until 22:00" do to how it feels to open this twenty times a day?
4. What is a camel doing in the name if it never appears in the product? If the empty, exhausted, and refilled states each had one, would this still be a widget any dashboard could ship?
5. At 3% with 40 minutes left, what do you want the user to *do*? Every decision in the panel is currently downstream of "display the data" rather than "change the user's next action".
